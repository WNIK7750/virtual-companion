# Git 与版本管理

## 分支

`main` 保存可审阅的集成源码。日常改动使用短期分支，完成后通过 PR 合并；目前不设置长期 `develop` 分支，避免两条主线反复同步。

- `feat/<topic>`：功能。
- `fix/<topic>`：修复。
- `docs/<topic>`：文档。
- `codex/<topic>`：自动化协作产生的工作分支。

PR 围绕一个具体问题，检查通过后优先 squash merge。合并后的短期分支可以删除；不要对公共 `main` 强制推送或改写历史。

## 提交与评审

提交信息推荐 `feat: ...`、`fix: ...` 等前缀。标题写最终改动，正文仅在需要解释原因或迁移方式时补充。

提交前检查实际暂存内容。源码、测试、无密钥示例和必要文档进入 Git；数据库、密钥、聊天原件、模型权重、缓存、依赖安装目录和构建物留在本机。

安装 [Gitleaks 8.30.1](https://github.com/gitleaks/gitleaks/releases/tag/v8.30.1) 后，在仓库根目录检查暂存内容：

```powershell
gitleaks git --pre-commit --staged --config .gitleaks.toml --redact=100 --ignore-gitleaks-allow .
```

GitHub Actions 另行扫描提交历史。扫描保留全部默认检测规则，例外仅匹配已审阅的具体文件及公开哈希或合成测试值；不得直接排除配置或测试目录。若真实凭据曾进入提交，先撤销或轮换凭据，再处理历史；只删除当前文件不能消除泄漏。

合并时核对行为、测试、数据影响及第三方许可。公开贡献不要求上传私人实验环境；使用可重复的合成最小例子。

## 版本

首次上传作为开发中的源码起点，不自动代表稳定发行。达到可使用的预览条件后，再使用 `v0.1.0-alpha.1` 一类带后缀的 tag 和 GitHub Pre-release；正式稳定版本另行决定。

tag 指向通过相应验证的固定提交。已发布 tag 不移动，修复创建新版本。Release 说明列出用户可感知变化、安装方式及必要兼容说明；源码 build 与安装包分别验证。

## 恢复

公共分支上的普通代码回退使用 `git revert` 并经过相同检查，保留协作历史。代码回退不会自动撤销数据库迁移、已发送请求或费用；涉及持久化时必须单独说明恢复方式。
